# 릴레이 프로토콜 v1 — pitwall ↔ cockpit

> **지위**: 이건 **계약**이다. 아직 구현 코드는 없다.
> 데몬(Go)과 서버(Python)가 각자 짜되 **이 문서와 `schema/v1/*.json` 을 SSOT 로 삼는다.**
> 한쪽만 고치는 변경 금지 — §12 의 변경 규칙을 따른다.

---

## 0. 이 프로토콜을 지배하는 질문 하나

> **"연결이 끊긴 순간 무엇이 남는가?"**

프로토콜 선택(MQTT), 절단선(stop 가격 push), 언어(Go)를 각각 고른 게 아니라 이 질문 하나가 셋을
동시에 결정했다. 아래 설계 판단이 애매해질 때마다 **취향 논쟁 대신 이 질문으로 돌아온다.**

끊긴 뒤 남는 것:

| 남는 것 | 근거 |
|---|---|
| 브로커에 걸어둔 **TP 지정가** | 데몬도 서버도 죽어도 체결됨 |
| 마지막으로 받은 **stop 가격** | retained 스냅샷이 로컬 디스크에 있음 |
| **로컬 타이머** (시간청산 · 데드맨 · 15:15 강제청산) | 네트워크 무관 |
| 서버측 **부재 감지** | LWT 가 브로커에서 자동 발행 |

남지 않는 것: **신규 진입**. 그래서 진입은 TTL 로 만료시켜 없애고(§9), 청산은 절대 만료시키지 않는다.
진입 실패는 기회 상실(유한)이고 청산 실패는 손실 노출(무한)이라 — 이 비대칭이 전체 설계의 축이다.

## 1. 채널

**아웃바운드 MQTT over WSS (TCP 443) 단일 채널.** 인바운드 포트 없음, 공유기 설정 없음.

MQTT 를 고른 이유는 취향이 아니라 이 프로젝트 요구 2개가 **프로토콜 기본기능**이기 때문이다:

- **LWT (Last Will)** — 사용자 PC 가 꺼지면 브로커가 대신 부재를 알린다. 서버측 데드맨이 공짜.
  ★ 이게 원격 기능의 킬러다. 최악의 시나리오는 손실이 아니라 *"출근했는데 집 PC 꺼진 줄 모름"* 이다.
- **retained** — 재접속 시 마지막 목표상태를 즉시 받는다. 스냅샷 재동기가 공짜.

생 WSS 로 시작하면 재연결·세션·백프레셔·QoS 를 결국 손으로 재구현하게 된다.
★ **지연은 WSS 와 동일**(둘 다 persistent connection) — 프로토콜 선택은 지연 논쟁과 무관하다.

요청/응답 성격(원장 조회, 릴레이 자격증명 갱신, 릴리스 확인)은 **HTTPS REST 병행**. MQTT 로 억지로 밀지 않는다.

### 1.1 토픽

`{acct}` = 릴레이가 발급한 **불투명 계정 핸들**. ★ 증권사 계좌번호가 아니다(§11).

| 토픽 | 방향 | QoS | retained | 내용 |
|---|---|---|---|---|
| `yovel/v1/{acct}/dn/target` | 서버→클라 | 1 | **✔** | `intent.target` — 목표상태 **전체 스냅샷** |
| `yovel/v1/{acct}/dn/cmd` | 서버→클라 | 1 | ✘ | `cmd.derisk` — de-risk 명령 |
| `yovel/v1/{acct}/up/state` | 클라→서버 | 1 | **✔** | `state.snapshot` — 현재 실상태 |
| `yovel/v1/{acct}/up/event` | 클라→서버 | 1 | ✘ | `event.order` — 주문·체결·청산 |
| `yovel/v1/{acct}/up/ack` | 클라→서버 | 1 | ✘ | `ack` — 다운링크 처리 결과 |
| `yovel/v1/{acct}/up/hb` | 클라→서버 | 1 | ✘ | `heartbeat` |
| `yovel/v1/{acct}/up/presence` | 클라→서버 | 1 | **✔** | `presence` — 온라인 여부. **LWT 가 여기에 발행** |

★ `presence` 를 `state` 와 **분리한 이유**: LWT 는 retained 로 발행되므로 같은 토픽에 두면
PC 가 꺼지는 순간 마지막 상태 스냅샷을 덮어써 지워버린다. 부재 표시가 상태 기록을 삭제하면 안 된다.

★ 브로커 ACL: 클라 자격증명은 `{acct}` 하위의 `dn/*` 구독 + `up/*` 발행만 허용. 옆집 계정 토픽 접근 불가.

## 2. 신뢰 모델 — 2층 (★ README §2 정정)

이 저장소 README §2 는 *"서버가 보낼 수 있는 명령은 de-risk 만, '사라'는 프로토콜에 아예 없다"* 고 썼다.
그런데 같은 README 첫 줄은 *"판단은 서버가 하고, 주문은 여기서 나간다"* 이다. 둘은 동시에 참일 수 없다.

**정정**: 문제의 주체는 "서버" 하나가 아니라 **둘**이었다.

```
  pitwall (전략 · 서명키 보유)  ──sign──▶  intent { entry, stop, tp, ver, exp }
                                              │
                                     릴레이 (중계만 · 서명 못 함)
                                              │
                                              ▼
                                          cockpit (공개키 pin)
```

| 주체 | 할 수 있는 것 | 털리면 최악 |
|---|---|---|
| **pitwall 서명키** | 진입 포함 전체 intent | 진짜 사고. 그래서 키는 릴레이에 두지 않는다 |
| **릴레이 서버** | 중계 · 지연 · 드롭 · (§2.2 켜면) de-risk | **봇이 꺼짐** — 복구 가능 |

즉 *"릴레이는 사라고 못 한다"* 가 맞는 서술이고, *"프로토콜에 BUY 가 없다"* 는 틀린 서술이다.
클라는 pitwall 공개키를 **바이너리에 pin** 하므로, 릴레이를 장악해도 서명 없는 진입은 만들 수 없다.

### 2.1 서명

- 알고리즘 **Ed25519**. `kid` 로 키 회전(겹치는 유예기간 동안 구/신 키 동시 수용).
- 서명 대상 = **`sig` 를 제외한 봉투 전체를 [RFC 8785 JCS] 로 정규화한 바이트**.
  (부분 필드만 서명하면 서명 안 된 필드로 의미를 바꾸는 공격이 열린다.)
- 검증 실패 = **드롭 + `ack{E_SIG}` + 긴급 알림**. 조용히 무시하지 않는다 —
  서명 실패가 조용하면 릴레이 장애와 공격이 구분되지 않는다.

### 2.2 ★ 미서명 de-risk — 명시적으로 켜고 끄는 손잡이

클라 설정 `accept_unsigned_derisk` (기본 **on**).

- **on**: 릴레이 세션 인증만 통과하면 `cmd.derisk` 를 서명 없이도 수용한다.
  얻는 것 = 서명키를 잃어버려도 전 사용자 봇을 세울 **탈출구**.
  잃는 것 = 릴레이가 털리면 공격자가 강제청산을 걸 수 있음(= 위 표의 "봇이 꺼짐", 설계상 수용 범위).
- **off**: 모든 다운링크가 서명 필수. 서명키 사고 시 탈출구가 사라진다.

★ 어느 쪽이든 **진입은 서명 없이 절대 통과하지 않는다.** 이 손잡이는 de-risk 에만 적용된다.

### 2.3 재생(replay) 방어

- 봉투마다 `nonce`. 클라는 최근 nonce 를 **`exp` 지나기 전까지** 기억하고 중복이면 `E_REPLAY`.
- retained `dn/target` 은 재접속마다 같은 메시지가 다시 오는 게 **정상**이다 → nonce 가 아니라
  `seq` 로 판정한다(§9.3). 이 둘을 헷갈리면 재접속 때마다 정상 스냅샷을 replay 로 버린다.

### 2.4 계정 바인딩 — ★ 사용자가 둘 이상이 되는 순간 생기는 공격면

클라는 **자기 `acct` 가 아닌 봉투를 거절한다** (`E_ACCT`). 서명이 유효해도 거절이다.

혼자 쓸 때는 없던 구멍이다. 사용자가 여럿이면 릴레이는 이렇게 할 수 있다:

> A 에게 갈 **진짜 서명된** `intent.target` 을 **B 에게 배달한다.**
> 서명 검증은 통과한다 — 피트월이 실제로 서명한 메시지다. B 는 A 의 목표를 자기 계좌에 집행한다.

즉 §2 의 2층 모델은 **"릴레이는 지시를 지어낼 수 없다"** 까지만 보장하지
**"릴레이는 지시를 엉뚱한 데로 보낼 수 없다"** 는 보장하지 않는다.
서명은 *누가 만들었나*를 증명하지 *누구에게 가는 것인가*를 증명하지 않기 때문이다.
토픽 ACL(§1.1) 은 방어의 한 겹이지만 서버측 설정이라 **클라가 확인할 수 없다** —
확인할 수 있는 쪽에도 같은 검사를 둔다.

- 검사 위치 = **서명 검증보다 앞.** 남의 봉투가 `seq`/`nonce` 상태를 건드리지 못하게 한다
  (아니면 남의 seq 로 내 카운터를 밀어올려 진짜 목표를 막을 수 있다).
- `acct` 는 봉투 안에 있고 **서명 대상에 포함**되므로, 릴레이가 배달 주소만 바꿔치기할 수는 없다.
  바꾸면 서명이 깨진다.
- 클라 설정이 비어 있으면 검사하지 않는다(릴레이 이전의 루프백 개발). 대신 데몬이 기동 시 경고한다.
  ★ 릴레이 등록이 붙으면 발급받은 `acct` 가 자동으로 채워지므로, 그때부터는 빈 값이 나올 수 없다.

## 3. 봉투 (envelope)

모든 메시지는 동일한 봉투를 쓴다. 스키마 = `schema/v1/envelope.schema.json`.

```json
{
  "v": 1,
  "typ": "intent.target",
  "id": "01J9Z8QK3M7X2ABCD",
  "acct": "acc_7f3a",
  "ts": "2026-08-15T09:05:00.000Z",
  "exp": "2026-08-15T09:06:00.000Z",
  "nonce": "b7d1e2f0",
  "seq": 10432,
  "body": { }
}
```

| 필드 | 의미 |
|---|---|
| `v` | 프로토콜 메이저. 토픽 경로의 `v1` 과 반드시 일치 |
| `typ` | 메시지 타입(§4·§5). 모르는 타입 = 무시 + `ack{E_UNSUPPORTED_TYPE}` |
| `id` | ULID. **멱등키** — 같은 `id` 재수신은 무해해야 한다 |
| `acct` | 불투명 계정 핸들 |
| `ts` | 발행 시각(UTC, 밀리초) |
| `exp` | 유효시각. **없으면 무기한이 아니라 스키마 위반**(진입은 반드시 있어야 함) |
| `nonce` | 재생 방어 |
| `seq` | `(typ, acct)` 별 단조증가 |
| `sig` | `{alg, kid, val}` — §2.1 |
| `body` | 타입별 본문 |

★ **알 수 없는 필드는 무시한다**(forward compat). 알 수 없는 필드가 있다고 거절하면 서버가 필드를
하나도 못 늘린다. 반대로 알 수 없는 **`typ`** 은 실행하지 않는다 — 모르는 명령을 추측 실행하면 안 되니까.

## 4. 다운링크 (서버 → 클라)

### 4.1 `intent.target` — ★ 이 프로토콜의 본체

**이벤트가 아니라 목표상태다.** "사라"를 쏘는 게 아니라 "이 계정의 목표는 이것" 을 통째로 내려보내고,
**클라가 실상태와 비교해 차이만 집행한다**(§6 reconcile).

이벤트로 쏘면 두 가지가 동시에 깨진다: 유실되면 그날 매매가 증발하고, 재전송하면 중복 주문이 난다.
09:00 윈도에서 30초만 끊겨도 둘 중 하나가 실제로 터진다.

★ **완성봉마다 전체 스냅샷을 재발행**한다. 포지션 하나의 stop 만 바뀌어도 전체를 다시 보낸다.
델타를 쓰면 "부분 상태 유실" 이라는 버그 계열이 통째로 생기는데, 이 규모(계정당 수 개 포지션 ×
분 단위)에선 전체 재발행 비용이 사실상 0 이다. retained 라 재접속 시 **한 통이면 완전 재동기**된다.

```json
{
  "as_of_bar": "2026-08-15T09:05:00+09:00",
  "book_state": "normal",
  "targets": [
    {
      "intent_id": "01J9Z8QK3M7X2ABCD",
      "slot": "gapdown_a",
      "symbol": { "exchange": "KRX", "code": "005930" },
      "side": "long",
      "want": "open",
      "weight": 0.14,
      "entry": {
        "mode": "market",
        "not_after": "2026-08-15T09:06:00.000Z",
        "max_slip_bp": 80
      },
      "exit": {
        "stop_price": 71200,
        "tp_price": 78400,
        "tp_delegate": true,
        "time_exit_at": "2026-08-15T15:15:00+09:00"
      }
    }
  ]
}
```

| 필드 | 계약 |
|---|---|
| `want` | `open` \| `flat`. **`flat` 이 곧 청산 지시** — 별도 SELL 메시지 타입을 두지 않는다 |
| `weight` | 슬롯 예산 대비 비중(0~1). ★ **원화 금액이 아니다** — §7 |
| `entry.not_after` | 이 시각 넘으면 **진입만** 포기. 청산·stop 은 계속 유효 |
| `entry.ref_price` | 사이징 기준가(선택). ★ 신호를 낸 쪽이 아는 값을 실으면 클라가 시세를 다시 조회하지 않는다 — 왕복이 줄고, 무엇보다 **신호를 낸 가격과 사이징한 가격이 갈리지 않는다** |
| `exit.stop_price` | 로컬이 지키는 숫자. **산식은 안 온다** — 서버가 매 완성봉 재계산해 결과만 내려보냄 |
| `exit.tp_delegate` | true 면 클라가 브로커에 **지정가로 위임**(끊겨도 체결되는 층) |
| `book_state` | `normal` \| `degrossing` \| `halted`. 포트폴리오 레벨 신호. 클라는 `halted` 면 신규진입 중단 |

★ **stop 은 로직이 아니라 숫자로 온다.** 트레일·계단을 클라에 구현하지 않는다. 이유 3개:
① 산식 이중구현 0 (Engine-as-SSOT 위반 없음) ② 은닉이 완벽 — 함수가 아니라 결과값만 감
③ **끊겨도 안전** — 마지막 stop 이 그대로 유효하고, 트레일이 *따라 올라가지 못할 뿐*이다.
최악이 "덜 잘 판 것" 이지 무방비가 아니다.

### 4.2 `cmd.derisk` — 나가는 방향만

```json
{ "action": "liquidate", "scope": "all", "reason": "operator", "until": null }
```

| `action` | 뜻 |
|---|---|
| `liquidate` | 대상 포지션 전량 시장가 청산 |
| `pause` | 신규 진입 중단. ★ **기존 포지션의 로컬 exit 은 계속 돈다** |
| `block_entry` | `pause` 와 동일하되 `until` 까지 자동 해제 |
| `resume` | 위 상태 해제 |

`scope` = `all` \| `slot`(+`slot`) \| `position`(+`intent_id`).

- de-risk 는 **항상 intent 를 이긴다.** 같은 틱에 진입 intent 와 pause 가 있으면 pause 가 이긴다.
- ★ **디스크에 영속**한다. 데몬을 재시작하면 풀리는 pause 는 안전장치가 아니다.
- `resume` 은 **사람의 명시적 행동**으로만. 타이머 자동 해제는 `block_entry.until` 하나뿐.

### 4.3 `intent.position` — 예약만, 구현 금지

포지션 1개의 stop 만 저지연으로 갱신하는 델타 메시지. **지금은 필요 없다**(§4.1 전체 스냅샷으로 충분).
타입 이름만 레지스트리에 잡아둬서, 나중에 필요해져도 `v1` 을 깨지 않고 추가할 수 있게 한다.

## 5. 업링크 (클라 → 서버)

### 5.1 `state.snapshot` (retained)

서버가 다음 intent 를 계산하려면 **실상태**가 필요하다. 이것도 이벤트가 아니라 스냅샷이다.

```json
{
  "as_of": "2026-08-15T09:05:03.120Z",
  "daemon": { "version": "0.1.0", "sha": "a1b2c3d", "started_at": "..." },
  "mode": "live",
  "applied_seq": 10432,
  "guards": { "paused": false, "block_entry_until": null, "circuit_breaker": false },
  "positions": [
    {
      "intent_id": "01J9Z8QK3M7X2ABCD",
      "symbol": { "exchange": "KRX", "code": "005930" },
      "qty": 14,
      "avg_entry_price": 72100,
      "entry_at": "2026-08-15T09:01:12+09:00",
      "stop_armed": 71200,
      "tp_order_id": "K-88213",
      "unrealized_pct": -0.0125
    }
  ]
}
```

★ `daemon.sha` 를 매번 싣는다. *"업데이트했는데 옛 코드가 돌고 있음"* 드리프트는 이 프로젝트에서
이미 실제로 겪은 사고고, 사용자 PC 로 배포하면 그대로 재발한다. heartbeat 에 sha 가 있으면
같은 채널로 잡힌다.

★ `mode` (`paper`\|`live`) 는 **절대 생략 불가**. paper 와 live 를 합산해 보여주면 허위 표시가 된다
(실측: live 15건 −18,725원 / paper 63건 +49,884원 → 합치면 "+3만 수익"인데 실계좌는 손실).

### 5.2 `event.order`

주문 생애주기. 원장·지연 실측용이고 **제어 경로가 아니다**(제어는 스냅샷).

`phase` = `submitted` \| `filled` \| `rejected` \| `canceled` \| `exit_filled`.
`exit_reason` = `stop` \| `tp` \| `time` \| `derisk` \| `manual` \| `broker`.

★ `submitted_at` / `filled_at` / `signal_ts` 3종을 전부 싣는다 —
**신호 시각 → 체결 시각** 이 곧 이 프로젝트가 없애려는 지연의 크기다. 못 재면 개선도 증명 못 한다.

★ `signal_ts` = 그 목표 스냅샷의 **`as_of_bar`** 다. `entry.not_after` 를 대신 쓰면 안 된다 —
그건 진입 **마감시각(미래)** 이라 `filled_at − signal_ts` 가 음수로 나온다. 부호가 뒤집힌 지연은
비어 있는 것보다 나쁘다: 값이 채워져 있으니 아무도 다시 보지 않는다.
(실측 사고 2026-08-15 — 회귀 gate `TestSignalTSPrecedesFill`.)

### 5.3 `heartbeat`

`{ seq, ts, daemon_sha, uptime_sec, broker_ws: "up"|"down", clock_skew_ms }`

주기 기본 **20초**. 서버는 **3회 연속 미수신(60초)** 이면 긴급 알림.
★ `broker_ws` 를 따로 싣는 이유: 데몬은 살아있는데 **증권사 WS 구독만 끊긴** 상태가 실재하고,
그러면 봉 기반 exit 이 전부 조용히 정지한다. heartbeat 가 "정상"으로 보이는 게 최악이다.

### 5.4 `presence` (retained · LWT)

접속 시 클라가 `{"online": true, "since": ...}` 를 retained 발행.
LWT 로 브로커에 `{"online": false, "reason": "lwt"}` 를 미리 등록 → 비정상 종료 시 브로커가 대신 발행.
정상 종료 시엔 클라가 `{"online": false, "reason": "shutdown"}` 을 직접 발행한다.

### 5.5 `ack`

`{ ref_id, ref_seq, status: "applied"|"partial"|"rejected"|"expired"|"ignored", codes: ["E_..."], detail }`

**모든 다운링크에 대해 반드시 보낸다** — 거절도 침묵이 아니라 코드로. 침묵과 실패가 같아 보이면
서버는 "명령이 안 갔나 / 갔는데 거절됐나" 를 영원히 구분 못 한다.

## 6. reconcile — 이 프로토콜의 실행 규칙

클라는 `dn/target` 수신 시, 그리고 최소 **5초마다** 다음을 돈다:

```
actual  := 브로커 조회 + 로컬 원장 (SSOT = 브로커)
target  := 마지막으로 검증 통과한 intent.target
diff    := reconcile(actual, target)
```

| 상황 | 행동 |
|---|---|
| target 에 있고 actual 에 없음 · `want=open` · `not_after` 유효 | **진입** |
| target 에 있고 actual 에 없음 · `not_after` 지남 | 아무것도 안 함 + `ack{E_EXPIRED}` |
| target `want=flat` 인데 actual 에 있음 | **청산** |
| 양쪽에 있고 `stop_price` 다름 | 로컬 stop 갱신 (주문 아님) |
| 양쪽에 있고 `tp_price` 다름 · `tp_delegate` | 브로커 지정가 **정정** |
| target 에 없는데 actual 에 있음 | ★ **자동 청산하지 않는다** — `ack{E_ORPHAN}` + 알림만 |

★ 마지막 줄이 중요하다. "목표에 없으면 판다" 는 얼핏 깔끔하지만, **서버가 상태를 한 번 잘못 계산하거나
스냅샷이 잘리면 사용자의 수동 보유분까지 털어버린다.** 유령 포지션은 사람이 본다.

**가드레일** (전부 클라 로컬, 서버가 못 끄는 것):

- reconcile 틱당 최대 주문 수 (기본 5) — 폭주 차단
- 같은 `intent_id` 는 **한 번만 진입**. 종결된 intent_id 는 영속 원장에 남아 재진입 불가 (`E_TERMINAL`)
  ★ 이게 없으면 stop 에 털린 자리에 같은 목표로 곧바로 재진입한다 — retained 목표는 재접속마다
  그대로 다시 오고, 진입 창(`not_after`)이 아직 안 지났을 수 있기 때문이다
- 진입은 `not_after` + 장 운영시간 + `guards` 전부 통과해야
- ★ **스냅샷 나이 > `target_max_age`(기본 180초) 면 진입 금지, 청산·stop 은 계속 동작**
  ("연결이 끊긴 순간 무엇이 남는가" 의 직접적 구현)

## 7. ★ 사이징은 클라가 한다

서버는 `weight`(비중)를 보내고, 클라가 **자기가 아는 자본**으로 수량을 계산한다.

```
qty = floor( weight × slot_capital / price / lot_size )
```

이유 3개:

1. **잔고가 와이어에 안 오른다.** 서버가 수량을 계산하려면 잔고를 알아야 하고, 그러면 §11 의
   프라이버시 티어가 무너진다.
2. ★ **whole-share 는 로컬에서만 정직하다.** 백테는 분수 주식으로 도는데 라이브는 정수로 내림된다.
   소액 계좌에서 `floor` 는 비중을 크게 왜곡하고, 그건 가격·틱·계좌를 다 아는 클라만 정확히 안다.
3. 증권사별 최소주문금액·호가단위·증거금이 전부 다르다. 서버에 그 표를 복제하면 그 표가 낡는다.

★ 계산 결과가 **0주면 진입 안 함 + `ack{E_CAPITAL}`**. 조용히 1주 사는 것 금지 — 그건 비중이 아니다.

## 8. exit 3층 (이 프로토콜이 지키는 것)

| 층 | 담당 | 프로토콜에서의 표현 | 끊기면 |
|---|---|---|---|
| 브로커 위임 | TP | `exit.tp_delegate` → 클라가 지정가 등록 | **그대로 체결** |
| 클라 로컬 | stop · 시간청산 · 데드맨 | `exit.stop_price` / `time_exit_at` | **그대로 동작** |
| 서버 명령 | 포트폴리오 디그로스 · 긴급 de-risk | `cmd.derisk` / `book_state` | 안 옴 |

3층에는 **로컬로 표현 불가능한 것만** 둔다. 로컬로 표현 가능한 걸 서버에 두면 가용성만 잃는다.

## 9. 시간 · 순서 · 거절

### 9.1 TTL

- `exp` 는 **봉 경계에 앵커**한다. "60초 뒤" 같은 상대시각은 지연 누적에 취약하다.
- ★ 진입은 `not_after` 가 **필수**. 끊겼다 붙은 클라가 철 지난 BUY 를 집행해 고점 매수하는 사고를
  구조적으로 차단한다.
- ★ 청산·stop 은 **만료시키지 않는다.** 만료된 stop 은 무방비이고, §0 의 비대칭에 정면으로 어긋난다.
  `exp` 가 지난 target 스냅샷도 **exit 부분은 계속 유효**하다 — 진입만 죽는다.

### 9.2 시계

클라는 `|ts − now|` 가 `max_skew`(기본 120초) 넘으면 `E_SKEW`. 단 **자기 시계를 맹신하지 않는다**:
skew 가 지속되면 거절이 아니라 **알림**을 올린다(사용자 PC 시계가 틀어진 게 흔한 원인).
로컬 타이머는 벽시계가 아니라 **monotonic clock** 으로 잰다.

### 9.3 seq

`dn/target` 은 `(acct)` 별 단조증가. `seq ≤ applied_seq` 면 **조용히 무시**(에러 아님) —
재접속 시 retained 로 같은 메시지가 다시 오는 건 정상 동작이다.
서버는 `state.snapshot.applied_seq` 로 유실을 **감지**한다. 복구는 되감기가 아니라 **재발행**이다.

### 9.4 거절 코드

| 코드 | 뜻 |
|---|---|
| `E_SIG` | 서명 검증 실패 / 모르는 `kid` |
| `E_EXPIRED` | `exp` 또는 `not_after` 경과 |
| `E_SKEW` | `ts` 가 허용 오차 밖 |
| `E_REPLAY` | nonce 중복 |
| `E_SCHEMA` | 스키마 위반 |
| `E_UNSUPPORTED_TYPE` | 모르는 `typ` |
| `E_MODE` | paper 모드라 실주문 안 함 |
| `E_PAUSED` | 로컬 de-risk 발효 중 |
| `E_MARKET_CLOSED` | 장 운영시간 밖 |
| `E_SYMBOL` | 모르는/거래정지 종목 |
| `E_CAPITAL` | 자본 부족 또는 `floor` 결과 0주 |
| `E_LOCAL_GUARD` | 서킷브레이커·일일한도 등 로컬 가드 |
| `E_BROKER` | 증권사가 거절 (`detail` 에 원문 코드) |
| `E_ORPHAN` | 목표에 없는 실보유 포지션 발견 (자동청산 안 함) |
| `E_RATE` | reconcile 틱당 주문 상한 초과 |
| `E_ACCT` | 이 클라의 `acct` 가 아닌 봉투 (★ 서명이 유효해도 거절) |
| `E_TERMINAL` | 이미 종결된 `intent_id` 로 다시 진입하려 함 |

## 10. 프라이버시 — 두 가지를 헷갈리지 말 것

**제어에 필요한 최소치**와 **원격 조회용 보관 티어**는 다른 문제다.

- **제어 최소치** (안 보내면 프로토콜이 성립 안 함): `intent_id`, 종목, 수량, 체결가, 손익.
  서버가 stop 을 재계산하려면 체결가를 알아야 한다. 협상 대상이 아니다.
- **보관 티어** (서버 DB 에 남기고 원격 UI 에 띄우는 범위):

  | 티어 | 내용 | 기본 |
  |---|---|---|
  | 0 | 손익% · 포지션 수 · heartbeat · 슬롯 상태 | 항상 |
  | 1 | 종목명 · 수량 · 원화 금액 | 동의 시 |
  | ✘ | **API 키 · 시크릿 · 증권사 계좌번호** | **절대 불가** |

★ `acct` 는 릴레이가 발급한 불투명 핸들이다. 계좌번호를 해시해서 쓰지 않는다 —
계좌번호는 공간이 좁아서 해시가 사실상 원문이다.

★ 원격 UI 는 전 화면에 `as-of HH:MM (n분 전)` 을 박고 오래되면 회색 처리한다.
지하철·엘리베이터에서 캐시된 옛 상태를 현재처럼 보여주는 게 이 UI 의 최악 실패다.

## 11. 버전 · 호환

- 메이저 = **토픽 경로**(`yovel/v1/...`) + 봉투 `v`. 둘이 다르면 `E_SCHEMA`.
- **v1 안에서 허용**: 선택 필드 추가 / 새 `typ` 추가 / 새 거절코드 추가 / enum 값 추가(수신측은
  모르는 값을 안전한 쪽으로 해석 — 예: 모르는 `book_state` 는 `halted` 로 취급).
- **v2 가 필요한 변경**: 필드 삭제·의미 변경·필수화, 토픽 재배치, 서명 대상 변경.
- 전환은 **양쪽 동시 배포 금지**. 서버가 `v1`·`v2` 를 병행 발행하고, 클라가 다 넘어간 뒤 `v1` 을 내린다.

## 12. 이 문서를 고치는 규칙

1. `docs/protocol.md` 와 `schema/v1/*.json` 은 **한 커밋에서 같이** 바뀐다.
2. 스키마를 고치면 `schema/examples/` 예제도 같이 고친다. `npm test` 가 예제를 스키마로 검증한다.

   먼저 여기서 합의하고 나서 코드를 고친다.

## 13. 미결

- **릴레이 브로커 선택** — 자체 운영(EMQX/Mosquitto) vs 관리형. ACL·자격증명 발급 흐름이 여기 딸림.
- **클라 자격증명 부트스트랩** — 사용자가 처음에 무엇을 붙여넣는가. 기기별 토큰? 로그인 후 발급?
- **`slot_capital` 의 소유자** — 사용자가 UI 에서 정하나, pitwall 이 `weight` 로 이미 표현하나.
  현재 계약은 "클라 소유"인데, 슬롯 간 자본 경합(공유풀)은 서버만 아는 정보라 긴장이 있다.
- **키 회전 절차** — `kid` 로 표현은 되지만 실제 배포 시퀀스(바이너리 pin 갱신)가 미정.
- **paper 모드에서 업링크를 보내는가** — 보내면 서버가 A/B 를 볼 수 있고, 안 보내면 유출면이 준다.
